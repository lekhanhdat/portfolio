## Context & problem

Began as my graduation thesis at VKU; I continue to develop and maintain it.

Da Nang recorded nearly 9.3 million visitor stays at accommodation establishments in the first ten months of 2024 ([Da Nang Newspaper](https://baodanang.vn/da-nang-don-gan-9-3-trieu-luot-khach-luu-tru-trong-10-thang-nam-2024-3143784.html), citing the Da Nang Statistics Office).

Visitors to Da Nang switch between many apps to find places, events and directions, get little cultural context about what they are looking at, and face language barriers without help outside office hours. The project brings these needs into one product: a mobile app for visitors and a web dashboard for the people who curate its content.

## Solution & ecosystem

The mobile app and the dashboard share one curated dataset of places, festivals and cultural objects. A FastAPI service handles semantic search, the chat assistant, image recognition and payments; an Express API serves the dashboard.

## Web admin dashboard

A React, TypeScript and Ant Design dashboard for administrators.

- Manage locations, festivals, cultural objects, users, reviews and transactions, with summary statistics on the home page.
- Data tables with server-side pagination, search, filtering and sorting.
- Create and edit forms in modals, delete confirmations and visibility toggles.
- JWT authentication with an admin role, backed by an Express API with rate limiting and security headers.
- Retries with exponential backoff and staggered API loading to stay within rate limits.

## Mobile app

A React Native and TypeScript app for visitors.

- **Discover:** places, festivals, reviews and historical objects, with detail pages and recommendations.
- **Navigate:** Mapbox maps with GPS, turn-by-turn and voice navigation, route alternatives, traffic and marker clustering.
- **Recognize:** an AI camera that identifies landmarks and objects from a photo.
- **Ask:** a chat assistant that accepts images and renders markdown answers with quick replies.
- **Festivals & newsfeed:** filters, calendar reminders, favorites, and shareable news articles.
- **Multilingual:** Vietnamese and English UI, with Azure Translator and cached translations for content.
- **Donate:** PayOS QR donations with transaction history.

## Architecture

**At launch**, the system had four layers:

- **Clients:** the React Native mobile app and the React admin dashboard.
- **APIs:** a FastAPI service (Python) for search, the chat assistant, image recognition and payments, and an Express API (Node.js) for the dashboard.
- **Data:** NocoDB for places, festivals, objects, users and transactions, and FAISS indexes for semantic search.
- **External services:** OpenAI, Mapbox, PayOS, SerpAPI, SendGrid and Azure Translator.

**Now**, the backend is being migrated to Google Cloud Run with Neon PostgreSQL. The core catalog API already runs there; AI, payment and account features are being re-enabled step by step behind feature flags.

## Engineering decisions

- **Plan for slow AI calls:** client-side timeouts, loading states and retries.
- **Control cost and accuracy:** similarity thresholds, curated data before the language model, and cached translations.
- **Degrade gracefully:** keyword search when semantic search fails, and feature flags that keep the app usable during the migration.
- **Keep the dashboard fast:** server-side search and filtering, retries with backoff and staggered requests.
- **Translate data, not only the UI:** pre-translated content plus cached runtime translation.

## Challenges & lessons

### Keeping the search index in sync with the data

Semantic search started returning duplicates and stale matches. The indexing script appended new embeddings to the existing FAISS index instead of replacing it, so after I added long descriptions to the embedded text, old and new vectors for the same places lived side by side. Separately, a parameter name that differed between the app and the API made some searches return nothing at all. I rebuilt the indexes from scratch and verified their size, added a startup check that rebuilds missing indexes, and aligned the request contract on both sides.

**Lesson:** treat a vector index as derived data — rebuild it from the source, check its size against the record count, and keep the client–API contract typed on both sides.

### Working within the limits of the data backend

The no-code database behind the first version returned at most 100 records per page, so some places silently never reached the app or its search. The dashboard also fired several heavy requests at once and hit rate limits. I added full pagination, a short-lived in-memory cache on the device, rate limiting and request timeouts on the dashboard API, retries with exponential backoff, and staggered loading of dashboard data.

**Lesson:** learn a data source's limits before building on it, and design clients to retry, back off and spread out their requests.

### Making slow, paid AI calls feel dependable

Image recognition goes through an upload, a visual search and two model calls, so it can be slow or fail on a weak connection. I added a preview step before upload, a server connection check, longer client timeouts, and fallbacks at every stage — keyword search when semantic search fails, curated descriptions before generated ones, and cached translations.

**Lesson:** design the experience around latency and failure from the start, and spend a paid API call only when cheaper data cannot answer.

### Bringing the project back on new infrastructure

After a pause, the original hosting and data store needed to be replaced. I migrated the data to PostgreSQL on Neon and the API to Google Cloud Run in small phases, each with its own checks: schema, import, local API, health endpoints, container, deploy and acceptance. The mobile app first came back in a read-only core mode, with the remaining features behind feature flags, and I put spending limits in place before the first deploy.

**Lesson:** migrate in small, verifiable steps, keep a working core at every step, and set cost limits before going live.
